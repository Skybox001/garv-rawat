PROJECT 01

Production RAG Chatbot

A retrieval model kept returning plausible but wrong chunks, so downstream answers failed. The question was whether the retriever itself was the bottleneck, and how much of the gap was actually recoverable.

ResultRecall@10 improved from 77.8% to 86.7% by fine-tuning all-MiniLM-L6-v2 with MultipleNegativesRankingLoss, measured on 45 held out questions over a 346 chunk corpus. Recall@1 also gained 8.9 points, from 42.2% to 51.1%. The eval split is kept separate from training, so the numbers are not self graded.

MethodGenerated a synthetic question per chunk with Llama-3.1-8B, then contrastively fine-tuned the bi-encoder on an 85/15 split using MultipleNegativesRankingLoss, the standard objective for this setup. The eval split is written to a separate file and never touched during training, so the reported numbers are not self graded. Also diagnosed a corpus problem where PDF structural elements such as the table of contents crowded out body prose, which inflated similarity scores on uninformative chunks.

PROJECT 04

QA Retrieval Failure Analysis

A TF-IDF retrieval baseline over 195 deduplicated SQuAD contexts and 1,500 questions, built to find out when lexical search actually breaks and why.

What I foundFailures clustered by question type, not uniformly. Low lexical overlap questions scored 42.7% Recall@5 against 97.5% for high overlap questions, a 2x gap driven entirely by wording that shares no terms with the source passage. The average hid the problem, which is the argument for slicing metrics by question type.

What fixed themA sentence embedding retriever, built as a controlled comparison on the identical split, closed a 33 point accuracy gap on the low overlap bucket while TF-IDF stayed stronger on high overlap and exact term queries. Neither model wins outright, so the fix is routing by question type rather than picking one retriever and hoping.
